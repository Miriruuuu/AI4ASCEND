# GPU 加速可行性：实测结论 + 可跑的基准

> 结论先说：**GPU 在"批量叶子评估"上真的快 18 倍，但它救不了 α-β 搜索。**
> 这里保留的是**实测证据**和一个**零依赖**的 WebGPU 基准，用来回答"值不值得做"。

## 1. 怎么跑

```bash
# ① 纯批量打分的微基准（人造大批量）
node scripts/gpu/run-gpu-bench.mjs            # 默认 65536 局面 × 5 次
node scripts/gpu/run-gpu-bench.mjs 262144 5   # 更大批量
BROWSER=edge node scripts/gpu/run-gpu-bench.mjs

# ② 决策级端到端实验（这才是"接进搜索值不值"的判据）
npx tsx scripts/gpu/decision-bench.ts 8 24    # 8 个真实中盘局面，每 24 手取一个
```

也可以直接双击 `webgpu-eval.html`（在 URL 后面加 `#auto` 会自动跑一遍）。

**零 npm 依赖**：Node 没有内置 WebGPU，但 Chrome 自带；而 **Node 22 内置 `fetch` + `WebSocket`**，
所以用 Chrome DevTools Protocol 直接驱动 headless Chrome 就够了 —— 不需要 Dawn/OpenCL 原生绑定，
也不往工程里塞任何包。

## 2. 实测结果（本机：Intel Xe2 核显 / 6 核 12 线程 / Chrome 154）

被搬上 GPU 的是**棋盘评估里最重的内层循环**：对每个局面扫描 **180 个 4 连窗口**打分。
这是搜索里**唯一真正适合 GPU 的形态** —— 局面之间独立、窗口之间独立、**控制流完全一致（无分歧）**。

| 指标 | GPU（含上传 + 回读往返） | CPU 单线程（同一实现） | 比 |
|---|---|---|---|
| 65536 个局面 | **8.1 ms**（123.6 ms / 百万局面） | 149.6 ms（2282.7 ms / 百万局面） | **18.5×** |
| 结果一致性 | ✅ **与 CPU 逐位一致**（整数累加） | — | — |

**小批量交叉点**（一次决策只有几千个待评估节点，这才是真实场景）：

| 局面数 | GPU（往返） | CPU | 谁赢 |
|---:|---:|---:|---|
| 1 | 1.400 ms | 0.000 ms | CPU |
| 81 | 2.700 ms | 0.100 ms | CPU |
| 512 | 2.900 ms | 1.000 ms | CPU |
| **4096** | **2.800 ms** | **8.400 ms** | **GPU** |
| 16384 | 3.700 ms | 34.300 ms | GPU |
| 65536 | 13.200 ms | 135.900 ms | GPU |

⇒ **交叉点 ≈ 1000~1500 个局面**；每次 dispatch + 回读有 **~1.4~2.9 ms 的固定往返成本**（与批量大小无关）。

## 3. 决策级实测：**接进真实决策，GPU 反而更慢**

上面第 2 节是"纯批量打分"的微基准（人工造的大批量、只有打分）。真实场景长什么样？
`decision-bench.ts` 回答了这个问题 —— 它用**真实引擎 + 现有 AI** 走出 8 个真实中盘局面，
对每个局面枚举**深度 2 的全部叶子**（我走一步 × 对手应对一步，平均 **5274** 个叶子/决策），
同一批叶子分别用 CPU 与 GPU 打分：

```bash
npx tsx scripts/gpu/decision-bench.ts 8 24
```

| 每个决策的耗时拆解 | 耗时 | 占比 |
|---|---:|---:|
| ① **叶子生成**（跑真实规则，**只能 CPU**） | **12.19 ms** | **71%** |
| ② CPU 单线程打分 | 4.96 ms | 29% |
| ③ **GPU 打分**（一次 dispatch） | **2.50 ms** | ← 打分环节快 **2.0×** |
| ④ 二进制传输（本实验走 http；真实集成用 `writeBuffer`） | 4.94 ms | — |

- **纯 CPU 端到端 17.14 ms/决策 ｜ GPU 端到端 19.62 ms（含传输）⇒ 端到端 0.87×（更慢！）**
- 就算把传输当 0（iGPU 共享内存、常驻 `writeBuffer`）：**也只有 1.17×**。
- 正确性：✅ GPU 与 CPU **逐位一致**。

### 为什么只有 1.17×，而不是第 2 节那个 18.5×

1. **批量太小**。真实决策只有 ~5k 个叶子，正好落在**交叉点附近**（第 2 节测得 1000~1500），
   每次 dispatch 的 ~1.4~2.9 ms 固定成本吃掉大部分收益 ⇒ 打分环节只剩 2.0×。
   第 2 节的 18.5× 是 65536 个局面的"大而整齐"批量，**不代表真实决策**。
2. **Amdahl：大头在 CPU 上，而且必须留在 CPU**。叶子生成要跑**有状态**的真实规则
   （棋盘 + 血量 + 植物 + 12 个技能 + 烈焰 + 高光……），跑在 CPU 上是 71% 的时间。
   把"评分"这一段搬上 GPU，**最多只能优化那 29%**。
   ⇒ 想靠 GPU 提速，就得让**模拟本身**也上 GPU，那等于用 WGSL 重写整个引擎 + 评估 + 全套技能规则。
3. 顺带一提：深度 2 穷举 ≈ 5274 个叶子，而**现有 AI 每次决策的确定性预算就是 15872 节点**，
   并且带剪枝、评估里还有植物/技能等项。
   ⇒ 即使 GPU 让这个"无剪枝、纯棋盘评估"的形态变快，它**在相同时间里搜得比现在更浅、评估信息更少**
   ⇒ 棋力会先倒退。

## 4. 实测结论

| 问题 | 答案 |
|---|---|
| GPU 打分比 CPU 快吗 | 在**大批量**（≥数万局面）上快 **18.5×**；在**真实决策规模**（~5k 叶子）上只快 **2.0×** |
| 接进真实决策能提速吗 | ❌ **不能**：端到端 **0.87×（更慢）**；把传输当 0 也只有 **1.17×** |
| 循环赛 / 对撞支持 GPU 了吗 | ❌ **没有，仍是 100% CPU**。`scripts/gpu/` 只是可行性实验，没接进任何搜索路径 |
| GPU 在这个项目哪里真有用 | **离线的超大批量打分**（百万级局面：调评估权重、生成训练数据）——那种批量才落在交叉点右侧 |



## 5. 为什么"结构上"也不该接进搜索热路径（除了上面实测的更慢）

1. **α-β 是串行的**：剪枝让后续节点依赖前面的搜索结果，**没法**把一次决策展开成一个独立大批量。
2. 单节点状态极小、开销在控制流与哈希查找上，本来就属于"GPU 最不擅长"的一类。
3. 要把 GPU 用起来，唯一可行的形态是"**放弃剪枝、批量评估叶子**"（GPU-Chess / GPU-MCTS 那一套）：
   把搜索变成固定深度、叶子一次性喂给 GPU。那要求评估函数**无状态且向量化**，
   并且**节点数会暴涨**（剪枝省掉的量级就没了）；更要命的是**评估里那些项（植物/技能/烈焰）
   都得能批量算** ⇒ 等于重写引擎。收益不确定、棋力还可能倒退。
4. 实际可用的替代方案已经存在且零成本：**按局多进程分片**（见 `scripts/duel-parallel.sh`），
   结果与串行逐字节等价。

## 6. 如果哪天真要用 GPU，这里已经铺好的部分

- `webgpu-eval.html` 里的 **WGSL 内核**是一份可直接复用的"**批量局面打分**"参考实现
  （输入：`count × 81` 的棋盘数组 + 180 个窗口偏移；输出：每局面一个 i32 分数）。
- `decision-bench.ts` 是一份"**决策级**端到端拆解"的模板：真实局面 → 枚举叶子 → CPU/GPU 打分对比
  （含 `startStaticServer` 走 http 传二进制的做法 —— `file://` 下 `fetch` 会被 CORS 挡死）。
- 接口约定：**整数累加**（浮点会有 ~3e-4 的 f32 舍入误差，实测过；引擎评估是整数，GPU 也应当位精确）。
- `cdp.mjs` 的 CDP 驱动是通用的：**任何**要跑 WebGPU/浏览器的实验都可以照抄它
  （起浏览器 → 连 WebSocket → `Runtime.evaluate({awaitPromise:true})`）。
- ⚠️ 一个限制：`dispatchWorkgroups(ceil(count/64))` 在 `count > 65535 × 64 ≈ 419 万` 时要改成二维 dispatch。

## 7. 顺带的降温手段（比 GPU 现实得多）

温度大致只随"**同时在跑的核心数**"走，与总工作量无关。本机实测（固定 32 局工作量）：

| 并发 `JOBS` | 墙钟 | 相对 8 并发 |
|---:|---:|---:|
| 8 | 11s | 基准 |
| 6 | 14s | +27% |
| 4 | 14s | +27% |
| 2 | 19s | +73% |

⇒ **并发砍到一半只慢约 27%**（不是翻倍）—— 想降温，`JOBS=4` 是性价比最高的一档。
另外 `COOLDOWN=30`（分批之间停 30s）、`NODES=8000`（把搜索预算减半）、
`powercfg ... PROCTHROTTLEMAX 80`（系统级限频，需管理员）都能进一步压温度。
